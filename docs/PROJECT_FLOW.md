# AI Interview System — Project Flow

## 1. What this project does

AI Interview System is a real-time mock-interview web application. A candidate uploads a resume and job description, receives a personalised interview plan, then answers questions by voice. The application transcribes the response, advances the interview, and speaks the next question.

```text
Candidate
  → React frontend
  → FastAPI backend
  → Resume/JD parsing and interview planning
  → WebSocket voice session
  → STT + VAD + question generation + TTS
  → browser playback and next candidate response
```

## 2. Technology used

| Area | Technology | Purpose |
|---|---|---|
| Frontend | React 18 + Vite | Interview UI, file uploads, microphone capture, transcript and audio playback |
| Backend | Python + FastAPI + Uvicorn | REST API, WebSocket server, interview orchestration |
| Data validation | Pydantic / pydantic-settings | API models and settings loaded from `backend/.env` |
| Resume parsing | `pdfplumber`, `python-docx` | Reads PDF and DOCX resume content |
| Job-description parsing | `pdfplumber` | Reads PDF job descriptions |
| LLM | Mistral (`mistralai`) | Generates project and skill questions when `MISTRAL_API_KEY` is configured |
| Speech to text (STT) | Faster-Whisper | Converts candidate PCM audio to text on CPU using INT8 inference |
| Voice activity detection (VAD) | `webrtcvad` | Detects speech and silence in candidate audio |
| Text to speech (TTS) | Kyutai Pocket TTS + PyTorch | Generates WAV speech for AI questions; supports catalog voices and voice cloning |
| Audio processing | Web Audio API, NumPy, SciPy, SoundFile | Browser PCM capture; backend audio conversion and WAV creation |
| State | In-memory `SessionStore` | Stores active uploads, plans, and transcripts for the current backend process |
| Deployment/dev tools | Docker Compose, Vercel, Render, Cloudflare Tunnel | Local containers and public frontend/backend access |

## 3. Main application flow

### Step A — Upload documents

1. The frontend sends the selected resume to `POST /upload/resume`.
2. The backend saves the file under `backend/uploads/`, extracts its text, parses resume data, and returns a `resume_id`.
3. The frontend sends the job description to `POST /upload/jd`.
4. The backend parses the JD and returns a `jd_id`.

Supported formats:

- Resume: PDF, DOCX, DOC, TXT
- Job description: PDF, TXT

### Step B — Start the interview

1. The frontend calls `POST /interview/start` with `resume_id` and `jd_id`.
2. The backend restores parsed uploads if a development reload cleared memory.
3. `interview_planner.py` creates a plan containing:
   - one introduction question;
   - two project questions;
   - one question for each extracted JD skill;
   - one closing question.
4. The backend creates an in-memory interview session and returns:
   - `interview_id`;
   - first question text;
   - current question number;
   - total question count;
   - JD skills.

Introduction and closing questions are fixed templates. Project and skill questions are generated by Mistral using the resume, JD requirements, and the candidate's previous answer. If no Mistral key is configured, a mock response keeps the UI runnable.

### Step C — Open the live voice channel

The frontend opens:

```text
WS /interview/voice/{interview_id}
```

The backend speaks the first question once the WebSocket connects. The session then repeats this loop:

```text
AI question → Pocket TTS WAV audio → browser playback
→ client sends audio_end → microphone opens
→ candidate PCM audio → VAD + Whisper STT
→ candidate answer committed → next question
```

## 4. WebSocket protocol and flags

### Client → server

| Message / data | Meaning |
|---|---|
| Binary WebSocket frame | Raw 16 kHz, mono, signed PCM16 candidate microphone audio. Frames are 20 ms / 320 samples. |
| `{"type":"audio_end"}` | The AI audio queue has finished playing. The backend can now accept candidate audio. |
| `{"type":"end_of_answer"}` | Candidate finished speaking. The backend immediately commits the buffered answer and advances the interview. |

### Server → client

| Message | Meaning |
|---|---|
| `partial_transcript` | Live Whisper text for one spoken segment. Includes ordered `seq` and `text`. |
| `transcript` | Final candidate answer, with `role: "candidate"`. |
| `thinking_start` | Backend is preparing the next turn. |
| `ai_text` | One text chunk that the AI is about to speak. |
| `audio_chunk` | Metadata for the following binary TTS WAV audio frame. |
| Binary WebSocket frame | WAV bytes generated by Pocket TTS. The frontend decodes it with `AudioContext.decodeAudioData`. |
| `ai_response` | The complete AI question or prompt. |
| `question_complete` | All AI text/audio chunks have been sent. When playback drains, the frontend sends `audio_end` and opens the microphone. |
| `listening` | No valid answer was detected; client should reopen the microphone. |
| `nudge` / `prompt_timeout` | A short prompt when the candidate has not responded. |
| `interview_complete` | No interview questions remain. |
| `error` | WebSocket/session error. |

## 5. Microphone, VAD, and answer submission

`frontend/src/hooks/useVoiceInterview.js` captures microphone audio with the Web Audio API, downsamples it to 16 kHz PCM16, and streams it to the WebSocket.

Two layers detect when an answer is complete:

1. Browser-side RMS silence detection sends `end_of_answer` after approximately **700 ms** of silence following detected speech. The **Stop & Send** button sends it immediately.
2. Backend `webrtcvad` tracks speech frames and provides segment, prompt, idle, and utterance states. It supports live partial transcription and a backend fallback if the client does not submit.

The backend ignores user audio until `audio_end` arrives. This prevents the AI's own spoken question from being transcribed through speaker echo.

## 6. Speech-to-text (STT)

File: `backend/app/services/stt_service.py`

- Provider: `faster-whisper` (fallback to `openai-whisper` if available).
- Default model: configured through `WHISPER_MODEL` (currently `base` unless changed in `.env`).
- Device: CPU.
- Compute type: INT8 to reduce CPU memory use.
- Input: raw 16 kHz mono PCM16 transformed into NumPy float32.
- Whisper is loaded lazily and reused as a singleton.
- Very short/silent chunks are skipped to reduce hallucinated filler text.

For low-memory hosting, use:

```env
WHISPER_MODEL=tiny
STT_MAX_CONCURRENCY=1
```

## 7. Text-to-speech (TTS) and voice cloning

File: `backend/app/services/tts_service.py`

- Provider: Kyutai Pocket TTS, running locally on CPU through PyTorch.
- Output: WAV bytes, streamed to the browser after each text chunk.
- Model and voice state are loaded once and reused for the server process.
- Questions are broken into short chunks using `text_chunker.py`, improving perceived response speed.

### Catalog voice

Use a Pocket TTS catalog name in `backend/.env`:

```env
TTS_PROVIDER=pocket
TTS_VOICE=alba
```

### Clone your own voice

1. Put a clean WAV sample in `backend/voices/`, for example:

   ```text
   backend/voices/sanjana-voice.wav
   ```

2. Configure the path relative to the `backend` directory:

   ```env
   TTS_VOICE=./voices/sanjana-voice.wav
   ```

3. Create a Hugging Face read token, accept the terms at `https://huggingface.co/kyutai/pocket-tts`, and add:

   ```env
   HF_TOKEN=hf_your_token_here
   ```

4. Restart the backend. `config.py` reads `HF_TOKEN`, and `tts_service.py` sets it before Pocket TTS loads the gated voice-cloning weights.

Only clone a voice you own or have explicit permission to use. Never commit the recording or token to a public repository.

### Memory note

Pocket TTS/PyTorch plus Whisper can exceed a 512 MB Render instance. Download caching reduces startup downloads but does **not** reduce runtime RAM. Use at least 1 GB RAM, remove local TTS/use browser speech, or use an external TTS provider for reliable deployment.

## 8. REST API summary

| Method | Endpoint | Use |
|---|---|---|
| `POST` | `/upload/resume` | Upload and parse resume |
| `POST` | `/upload/jd` | Upload and parse job description |
| `POST` | `/interview/start` | Create interview plan and session |
| `POST` | `/interview/answer` | Text-only fallback: submit an answer and receive the next question |
| `GET` | `/interview/{interview_id}/transcript` | Retrieve current in-memory transcript |
| `GET` | `/health` | Health-check endpoint; returns `{"status":"ok"}` |
| `WS` | `/interview/voice/{interview_id}` | Live audio interview channel |

## 9. Important environment variables

Backend file: `backend/.env`

```env
# LLM
MISTRAL_API_KEY=...
MISTRAL_MODEL=mistral-small-latest

# TTS
TTS_PROVIDER=pocket
TTS_VOICE=alba
HF_TOKEN=hf_...

# STT
WHISPER_MODEL=base
STT_SEGMENT_SECONDS=0.3
STT_SILENCE_SECONDS=8.0
STT_PROMPT_TIMEOUT_SECONDS=6.0
STT_NO_ANSWER_TIMEOUT_SECONDS=12.0
STT_MAX_CHUNK_SECONDS=1.5
STT_MAX_CONCURRENCY=2

# Backend
CORS_ORIGINS=http://localhost:5173,https://your-vercel-app.vercel.app
DATABASE_URL=sqlite+aiosqlite:///./interview.db
UPLOAD_DIR=./uploads
```

Frontend file: `frontend/.env`

```env
VITE_API_URL=https://your-backend-domain
```

`VITE_API_URL` must contain the backend base URL without a trailing slash. The frontend builds a `wss://` URL automatically when it sees an `https://` backend URL.

## 10. Deployment notes

- **Vercel**: hosts the React frontend. Add `VITE_API_URL` in Vercel Environment Variables and redeploy after changing it.
- **Render**: can host the FastAPI backend. Add `MISTRAL_API_KEY` and `HF_TOKEN` in Render Environment Variables.
- **Cloudflare Quick Tunnel**: exposes local `localhost:8000` temporarily. Its `trycloudflare.com` URL changes when restarted; update Vercel `VITE_API_URL` and redeploy each time.
- **CORS**: backend `CORS_ORIGINS` must include the exact Vercel frontend origin. Restart the backend after changing `.env`.
- **Docker Desktop**: must be running before `docker compose up --build` can work on Windows.

## 11. Current limitations and next improvements

- Active sessions and parsed metadata are in memory, so a backend restart clears them.
- SQLAlchemy/SQLite dependencies are installed, but durable session storage is not currently wired into the route flow.
- No login/authentication or per-user data isolation is implemented.
- Personal voice recordings should use private storage, not the public repository.
- The current live voice design is CPU-heavy; production scaling should use more memory, smaller models, or managed STT/TTS services.
